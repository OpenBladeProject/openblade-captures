# Запись USB-трафика неподдерживаемой модели Razer Blade

[English](../../CAPTURE_GUIDE.md) | [简体中文](../zh-CN/CAPTURE_GUIDE.md) | Русский

Это руководство предназначено для исследования протокола модели Razer Blade, которую OpenBlade пока не поддерживает. Оно не даёт разрешения на запись команд в устройство. Команда становится доступной в продукте только после прохождения всех проверок допуска из этого руководства для конкретной модели. Указывайте проверенную версию прошивки как сведения о происхождении доказательств; ограничивайте допустимые версии только тогда, когда этого прямо требует проверенное правило допуска.

<a id="safety-model"></a>
## Меры безопасности

1. Работайте непосредственно в Windows 11 с .NET SDK, Wireshark/tshark и USBPcap. Используйте приложение производителя только как эталон для наблюдений.
2. Пока USBPcap работает с целевым интерфейсом, служба OpenBlade должна быть остановлена. Универсальный сценарий записи сохраняет и восстанавливает её исходное состояние.
3. Записывайте по одному действию оператора. Не выводите команды из данных похожей модели и не объединяйте пробные записи команд.
4. Найдите и реализуйте операции чтения/запроса до проверки команды изменения настройки.
5. При каждой проверке записи сохраните ранее подтверждённое состояние, покажите точное предлагаемое изменение, получите подтверждение оператора, примените значение один раз, запросите результат и восстановите сохранённое состояние.
6. Останавливайте USBPcap только предоставленным вспомогательным инструментом для изолированной группы процессов. Никогда не вызывайте `GenerateConsoleCtrlEvent` с группой `0`: сигнал будет разослан родительской консоли и может завершить Codex или PowerShell.
7. Храните исходные записи локально. USB-трафик может содержать серийные номера, уникальные пути экземпляров устройств, нажатия клавиш и данные других устройств.

<a id="toolkit"></a>
## Инструменты

- `tools/Get-BladeCaptureInventory.ps1` собирает неуникальные сведения о модели, прошивке, Windows и USB-идентификаторах Razer.
- `tools/New-CaptureWorkspace.ps1` создаёт локальный сеанс, исключённый из Git, с версионируемым планом записи и журналом оператора.
- `tools/Invoke-InteractiveUsbPcapCapture.ps1` запускает USBPcapCMD в изолированной группе процессов, останавливает его адресным сигналом Ctrl+Break и восстанавливает исходное состояние службы OpenBlade. Для ограниченного сопоставления трафика нескольких устройств можно выбрать один или несколько проверенных адресов на одном корневом устройстве USBPcap.
- `tools/Convert-UsbPcapToTransactions.ps1` декодирует локальный PCAP с помощью tshark в записи транзакций с ограниченным объёмом данных.
- `tools/Compare-CaptureTransactions.ps1` сравнивает фоновую запись и запись одного действия. При вычислении смыслового отпечатка проверенных 90- и 374-байтовых пакетов Razer он исключает идентификаторы транзакций, контрольные суммы и неиспользуемое заполнение, сохраняя различия команд и полезных данных.
- `tools/New-SanitizedCaptureAnnotation.ps1` создаёт заготовку аннотации, пригодной для коммита, с хешами записей и результатами восстановления.
- `tools/Test-CaptureEvidence.ps1` проверяет происхождение, удаление чувствительных данных, ограничения объёма, хеши записей и восстановление. Перед коммитом проверяйте локальную запись с `-PcapPath`. Используйте `-SchemaOnly` только при намеренном отсутствии исходной записи.
- `tools/Test-UsbPcapShutdownSafety.ps1` проверяет, что завершение записи не может разослать Ctrl+C родительской консоли.

Два сценария сохраняют проверенное исследование контекста управления вентиляторами с охлаждающей подставкой для конкретного RZ09-0581 с BIOS 4.00:

- `tools/Invoke-CoolingPadFanContextCapture.ps1` записывает переходы Fixed/Auto, выполняемые Synapse: при активной передаче кадров подсветки, с погашенной подсветкой в том же сеансе процесса Synapse и после подтверждённого запуска нового сеанса процесса Synapse. OpenBlade остаётся остановленным и не отправляет HID-команд.
- `tools/Analyze-CoolingPadFanContextCapture.ps1` сравнивает три ограниченных маркерами интервала, требует точных подтверждений запросов Fixed/Auto, подсчитывает кадры подсветки и отделяет доказательства о сеансе процесса от нерешённого вопроса о том, кто владеет конкретным HID-дескриптором.

Другие сценарии `Analyze-*`, `Export-*`, `Get-*`, `Invoke-*` и `Start-*`, в именах которых указаны модели, сохранены как проверенные инструменты для конкретных устройств. Они могут выполнять изолированную запись поведения эталонного приложения, экспортировать ограниченный набор тестовых данных, повторять матрицу запросов только для чтения, проводить обратимую проверку или исследовать проверенный механизм производителя. Не используйте их как универсальные заготовки и не переносите их идентификаторы, интерфейсы, адреса, хеши, пути, структуру отчётов или байты команд на другую модель.

<a id="1-prepare-the-machine"></a>
## 1. Подготовьте компьютер

Установите:

- .NET 10 SDK;
- Wireshark с tshark;
- USBPcap;
- актуальное программное обеспечение производителя для этого ноутбука — временно.

Перед реальной записью выполните регрессионную проверку безопасного завершения:

```powershell
.\tools\Test-UsbPcapShutdownSafety.ps1
```

Соберите сведения без уникальных идентификаторов:

```powershell
.\tools\Get-BladeCaptureInventory.ps1 `
  -OutputPath .\raw\my-model\inventory.json
```

Проверьте результат. Он должен содержать номер модели Razer, BIOS, сборку Windows и пары VID/PID, но не серийный номер компьютера и не полные суффиксы экземпляров PnP. Возьмите версии EC и MCU из достоверного интерфейса или из позднее проверенного запроса; не угадывайте их.

Если исследуется работа через установленный драйвер Razer, инструкции по инвентаризации и экспорту пакета находятся в отдельном репозитории [`blade-driver-catalog`](https://github.com/OSSBlade/blade-driver-catalog). Этот репозиторий хранит доказательства о протоколе и проверках на оборудовании. Экспорты Driver Store и полные отчёты об экземплярах устройств остаются закрытыми.

Для конкретной Razer Laptop Cooling Pad (`1532:0F43`, ревизия USB `0200`) отдельно запишите USB-интерфейсы и структуру HID-отчётов:

```powershell
.\tools\Get-CoolingPadCaptureInventory.ps1 `
  -OutputPath .\raw\cooling-pad-interface-inventory.json
```

Этот сбор сведений открывает HID-коллекции с нулевыми запрашиваемыми правами доступа и вызывает только API дескрипторов и предварительно разобранных данных. Он не запрашивает и не записывает feature-отчёты и никогда не сохраняет путь интерфейса устройства, полный идентификатор экземпляра, идентификатор контейнера, путь расположения или серийный номер. У проверенного экземпляра есть одна коллекция с 91-байтовым feature-отчётом на `MI_00`. Это подтверждает наличие прямого HID-транспорта в пользовательском режиме, но ничего не говорит о смысле команд.

<a id="2-create-a-local-session"></a>
## 2. Создайте локальный сеанс

```powershell
$session = .\tools\New-CaptureWorkspace.ps1 `
  -RootDirectory .\raw `
  -ModelNumber RZ09-XXXX `
  -VendorId 1532 `
  -ProductId 0000 `
  -BiosVersion 0.00 `
  -Purpose "battery charge limit query"
```

Команда создаёт исключённый из Git каталог со следующим содержимым:

- `capture-plan.json`: точная цель, условия, действие, ожидаемое наблюдение, исходное состояние, контрольное чтение и восстановление;
- `operator-log.md`: отметки времени и заметки;
- пустые каталоги `baseline` и `action`.

Заполните план до записи. Для каждого изменяемого значения создавайте новый сеанс.

<a id="3-identify-usbpcap-root-and-device-address"></a>
## 3. Определите корневое устройство USBPcap и адрес устройства

Запустите вывод списка устройств USBPcapCMD в терминале с правами администратора и найдите цель по её аппаратному USB-идентификатору. Адреса могут измениться после переподключения, выхода из сна или перезагрузки, поэтому определяйте их заново для каждого сеанса. При неоднозначной идентификации остановитесь. Не записывайте все устройства только ради того, чтобы избежать поиска нужного.

Сценарий записи допускает `-AllDevices` только для изучения дескрипторов. Для записи действия используйте один `-DeviceAddress` либо `-DeviceAddresses`, когда одно действие нужно сопоставить на двух или более явно выбранных устройствах одного корневого устройства USBPcap. Никогда не заменяйте ограниченную запись нескольких выбранных устройств параметром `-AllDevices`.

<a id="4-capture-baseline-and-one-action"></a>
## 4. Запишите фон и одно действие

Запустите фоновую запись из PowerShell с правами администратора:

```powershell
.\tools\Invoke-InteractiveUsbPcapCapture.ps1 `
  -UsbPcapDevice \\.\USBPcap3 `
  -DeviceAddress 2 `
  -OutputDirectory $session.BaselineDirectory
```

Для ограниченной парной записи на одном корневом устройстве передайте проверенные временные адреса массивом. Определяйте их заново после каждого отключения или переподключения:

```powershell
.\tools\Invoke-InteractiveUsbPcapCapture.ps1 `
  -UsbPcapDevice \\.\USBPcap3 `
  -DeviceAddresses 2,5 `
  -OutputDirectory $session.ActionDirectory
```

Несколько секунд не выполняйте действий на нужной странице приложения производителя, затем создайте указанный сценарием сигнальный файл `capture.stop`. Повторите запись в каталоге действия, изменив ровно одно значение ровно один раз. Оставьте достаточно времени без действий до и после изменения.

Сценарий:

- запускает USBPcapCMD с `CREATE_NEW_PROCESS_GROUP`;
- сохраняет PID, идентификатор группы процессов, время запуска, исполняемый файл и сведения о принадлежности выходных файлов;
- отправляет `CTRL_BREAK_EVENT` только этой ненулевой группе из отдельного защищённого вспомогательного процесса;
- проверяет корректное завершение и непустой результат;
- восстанавливает службу OpenBlade только в том случае, если она работала до записи.

Интерактивный сценарий никогда не выбирает принудительное завершение автоматически. Если корректно завершить процесс не удалось, оператор может явно запустить `Stop-UsbPcapCapture.ps1 -ForceFallback` для сохранённого сеанса с данными о принадлежности процесса. Принудительное завершение может привести к потере пакетов в буфере; это необходимо указать в аннотации.

<a id="5-decode-and-compare"></a>
## 5. Декодируйте и сравните

```powershell
.\tools\Convert-UsbPcapToTransactions.ps1 `
  -PcapPath $session.BaselinePcap `
  -OutputPath (Join-Path $session.Root "baseline-transactions.json")

.\tools\Convert-UsbPcapToTransactions.ps1 `
  -PcapPath $session.ActionPcap `
  -OutputPath (Join-Path $session.Root "action-transactions.json")

.\tools\Compare-CaptureTransactions.ps1 `
  -BaselinePath (Join-Path $session.Root "baseline-transactions.json") `
  -ActionPath (Join-Path $session.Root "action-transactions.json") `
  -OutputPath (Join-Path $session.Root "comparison.json")
```

Декодер сохраняет номер кадра, относительное время, направление, конечную точку, поля setup, ограниченное шестнадцатеричное представление полезных данных и их длину. Считайте результат исходными данными, пока он не проверен и не очищен. Разница в полезных данных — кандидат для исследования, а не определение команды. Средство сравнения распознаёт пакеты Razer длиной 90 и 374 байта с корректной контрольной суммой, с префиксом идентификатора отчёта или без него. Оно игнорирует идентификатор транзакции, контрольную сумму, зарезервированные байты и неиспользуемое заполнение, но сохраняет статус, идентификатор отчёта, класс/идентификатор команды, длину и значимую часть полезных данных. Неизвестные или некорректные данные сравниваются целиком и побайтово.

Некоторые кадры успешного завершения управляющей передачи USBPcap содержат тело ответа, хотя Wireshark оставляет все поля полезных данных пустыми. Декодер выполняет второй проход `tshark -T json -x` с узким фильтром только для таких IN-кадров, удаляет объявленный псевдозаголовок USBPcap и помечает ограниченное тело как `UsbPcapFrameData`. Полные исходные кадры и метаданные IRP никогда не сохраняются. Этот резервный способ обязателен, прежде чем делать вывод об отсутствии ACK или ответа на запрос.

Сопоставляйте кандидатов со следующими данными:

- точной отметкой времени действия оператора;
- повторной записью того же значения;
- другим значением той же настройки;
- отрицательной контрольной записью без действия;
- соответствующим трафиком чтения/запроса.

Определите структуру отчёта, идентификатор транзакции, класс/идентификатор команды, длину полезных данных, контрольную сумму, статус ответа и байты, кодирующие значение. Удалите посторонние входные interrupt-отчёты и периодическую телеметрию.

<a id="6-build-a-query-first-fixture"></a>
## 6. Подготовьте тестовые данные, начиная с запроса

Пригодный для коммита набор тестовых данных запроса содержит:

- номер модели, VID, PID, BIOS, а также EC и MCU, если они известны;
- интерфейс/коллекцию и идентификатор отчёта;
- очищенный запрос и ожидаемый ответ;
- границы полезных данных и трактовку контрольной суммы;
- сопоставление транзакций и допустимый статус;
- хеш записи и версию декодера;
- отрицательные доказательства из соседнего трафика.

Реализуйте запрос в типизированной команде для разработчика. Она должна проверять точную идентичность устройства, отклонять некорректные или не соответствующие запросу ответы, ограничивать время ожидания и не позволять передавать произвольные полезные данные.

Повторно проверяйте запрос при следующих условиях:

- перезапуск службы;
- переподключение устройства;
- сон/возобновление работы;
- питание от сети, USB-C и батареи, где это применимо;
- запущенное и остановленное ПО производителя.

При сбое запроса результат должен становиться недоступным без выполнения записи.

<a id="7-validate-a-setter"></a>
## 7. Проверьте команду изменения настройки

Не используйте универсальные сценарии записи трафика для повторной отправки байтов. Добавьте проверенный типизированный план проверки в `plans`, проверяйте хеш его точных байтов в инструменте разработчика и показывайте план перед выполнением.

Интерактивный сценарий должен:

1. проверить точную модель, PID и допустимую прошивку;
2. запросить и показать исходное состояние;
3. показать точное изменение одного значения и его восстановление;
4. потребовать подтверждение;
5. применить одно значение;
6. выполнить контрольное чтение и сравнить результат;
7. восстановить исходное значение в `finally`;
8. запросить состояние после восстановления и сравнить его;
9. выдать результат ограниченного объёма без исходного трафика.

Без независимого контрольного чтения команда изменения не может подтвердить текущее состояние прошивки. OpenBlade может сохранять желаемые настройки профиля и повторно применять подсветку, когда это допускает включённая пользователем политика принудительного восстановления и пройдены свежие проверки безопасности. Нельзя повторять запись с неоднозначным результатом. Одного визуального подтверждения недостаточно для замены восстановления.

<a id="8-coverage-matrix"></a>
## 8. Матрица покрытия

Исследуйте только настройки, которые есть у целевого устройства, но явно отметьте каждую строку как поддерживаемую, отсутствующую, программную или неисследованную.

Скопируйте для цели `templates/device-coverage.template.json`. Вложенная матрица схемы 2 отдельно отслеживает каждый контекст питания, класс питания USB-C, вариант подсветки, группу цвета/длительности/направления/области, событие жизненного цикла, поведение при конфликте и тип сбоя. Оставляйте каждую возможность в состоянии `NotInvestigated`, пока доказательства не проведут её через запись трафика, проверку запроса, проверку изменения и допуск в продукт. Отмечайте отсутствующую функцию как `Absent`; не удаляйте строку и не объединяйте несколько вариантов одним статусом.

| Область | Минимальный набор записей |
| --- | --- |
| Идентификация | дескрипторы, модель, BIOS, EC, MCU, нужные интерфейсы |
| Производительность | каждый профиль для сети/USB-C/батареи, уровни Custom, контрольное чтение |
| Вентиляторы | Auto, границы и шаг фиксированного диапазона, максимум, ручные изменения, запрос RPM |
| Батарея | защита выключена, все заявленные пределы, временный полный заряд, запрос |
| Подсветка клавиатуры | Off, яркость, каждый эффект, все цвета/длительности/направления/области |
| Подсветка логотипа | каждый режим и запрос текущего значения |
| Поведение клавиатуры | Fn-primary, Gaming mode, анимация запуска, режим устройства |
| Специальные клавиши | исходные отчёты для каждого действия слоя Fn или отдельной аппаратной клавиши |
| Экран | режимы, видимые Windows, DRR, HDR, поведение цветового профиля |
| Жизненный цикл | холодный запуск, вход в систему, перезапуск службы, сон/возобновление, переподключение |
| Питание | полноценное питание от сети, каждый поддерживаемый класс USB-C, батарея, переходы |
| Конфликты | наличие контроллера производителя, внешнее изменение, явный возврат управления |
| Сбои | тайм-аут, некорректный ответ, неверная транзакция, неподдерживаемый PID |

Если эффект или настройка имеет несколько вариантов, запишите каждый из них, не предполагая наличие битового флага. Для эффектов, формируемых на компьютере, запишите и команду настройки, и достаточное количество кадров, чтобы установить формат матрицы и частоту передачи.

<a id="model-specific-helpers-and-evidence-ledgers"></a>
### Инструменты для конкретных моделей и реестры доказательств

Сценарии с именем модели привязаны к идентификаторам, интерфейсам, владению контроллером, ожидаемым файлам и границам безопасности проверенных сеансов. Перед повторным запуском изучите параметры и сохранённые доказательства, подтвердите точную модель и допустимую прошивку, используйте новый каталог вывода, исключённый из Git. Не ослабляйте жёстко заданные проверки идентичности, адреса, пути, подписи или хеша, чтобы запустить инструмент на другом компьютере.

Сохранённый инструмент обычно выполняет одну из следующих задач:

1. Обёртка записи эталонного приложения изолирует OpenBlade, определяет адрес USBPcap, оставляет PCAP локально и сохраняет файлы действий оператора и состояния записи.
2. Анализатор или экспортёр преобразует локальную запись в ограниченный очищенный набор тестовых данных, не ослабляя проверки идентичности, времени, контрольной суммы и структуры отчётов.
3. Матрица только для чтения повторяет типизированные запросы в подтверждённых оператором состояниях питания или жизненного цикла, предотвращает конкурирующее чтение и восстанавливает временно изолированную службу.
4. Средство обратимой проверки сохраняет состояние конкретного устройства, применяет одно ограниченное значение, независимо считывает его и восстанавливает исходное. Отклонённое изменение или успешное восстановление всё ещё может быть отрицательным доказательством, а не основанием для допуска команды изменения.
5. Средство исследования владения или жизненного цикла может установить, какой подписанный компонент производителя с закреплённым хешем владеет механизмом доступа. Владение, тайм-аут запроса значения или статический анализ не разрешают использовать драйвер ядра, зависимость от ПО производителя или команду изменения.

Используйте `decoded/*-device-coverage.json` как авторитетную матрицу статусов для конкретной модели и области прошивок. Соответствующий `decoded/*-evidence.json` может суммировать допущенный транспорт, настройки, поведение жизненного цикла и обработку сбоев. Другие декодированные наборы данных могут содержать ограниченные отчёты, эталонные данные эффектов, карты клавиш и результаты проверок. Соответствующие аннотации фиксируют происхождение, изоляцию, восстановление, отрицательные результаты и ограничения.

Продвигайте каждый конечный элемент покрытия независимо. Проверка базовой настройки или эффекта не означает автоматической проверки параметров, запроса значения, контрольного чтения, контекстов питания или жизненного цикла. Сохраняйте частичные доказательства ввода, если одни физические отчёты различимы, а другие нет. Проверка установленного интерфейса и регрессий подтверждает только поведение продукта; она не является ни командой прошивки, ни контрольным чтением устройства.

<a id="9-sanitize-and-validate"></a>
## 9. Очистите и проверьте данные

Создайте заготовку аннотации:

```powershell
.\tools\New-SanitizedCaptureAnnotation.ps1 `
  -PlanPath (Join-Path $session.Root "capture-plan.json") `
  -StatePath (Join-Path $session.ActionDirectory "capture.state.json") `
  -PcapPath $session.ActionPcap `
  -OutputPath .\annotations\YYYY-MM-DD-action.json
```

Замените заполнители проверенными доказательствами ограниченного объёма. Никогда не вставляйте весь поток полезных данных. Установите `action.kind` в `ReadOnlyQuery`, `SettingChange`, `Observation` или `NegativeControl`. Для каждого `SettingChange` нужны успешные результаты получения исходного состояния, применения, контрольного чтения, восстановления и контрольного чтения после восстановления. Используйте роль происхождения `OracleCapture`, `ReadOnlyQueryCapture`, `NegativeCapture`, `ExactDeviceInteractiveValidation` или `OpenBladeTypedValidation` и укажите имя и версию контроллера. Каждый элемент `sanitizedEvidence` должен содержать короткое поле `kind`, понятное человеку описание `summary` и только ограниченные поля, необходимые для воспроизведения вывода о протоколе. Затем выполните:

```powershell
.\tools\Test-CaptureEvidence.ps1 `
  -AnnotationPath .\annotations\YYYY-MM-DD-action.json `
  -PcapPath $session.ActionPcap
```

Валидатор отклоняет отсутствие сведений о происхождении, пустые записи или запись всех устройств без явного указания этого факта, нераскрытое принудительное завершение, отсутствие результатов восстановления, локальные пути, значения, похожие на серийные номера, неограниченные доказательства и расширения исходных файлов записи. Параметр `-PcapPath` обязателен перед коммитом: он сверяет сохранённые SHA-256 и размер в байтах с локальной исходной записью. При проверке уже закоммиченной аннотации без намеренно исключённого из Git PCAP используйте явный режим `-SchemaOnly`. Он проверяет схему и очистку данных, но сообщает, что хеш PCAP не был независимо проверен.

После изменения схем, сравнения, очистки, покрытия или другого поведения инструментов запустите автономные регрессионные проверки:

```powershell
& "$env:SystemRoot\System32\WindowsPowerShell\v1.0\powershell.exe" `
  -NoProfile -NonInteractive -ExecutionPolicy Bypass `
  -File .\tests\Run-All.ps1
```

В автоматизации используйте `-NonInteractive`. Одна регрессионная проверка намеренно не передаёт обязательный режим валидатора, чтобы убедиться, что выполнение безопасно отклоняется. Без этого параметра интерактивный PowerShell будет ждать ввода обязательного аргумента.

<a id="10-production-admission"></a>
## 10. Допуск в продукт

Возможность готова для таблицы поддержки OpenBlade только после независимого прохождения каждой проверки:

- зафиксированы точная область модели/PID, проверенная прошивка и любые явные ограничения прошивки;
- закоммичена хотя бы одна очищенная запись эталонного приложения;
- запрос и ответ декодируются детерминированно;
- проверены контрольная сумма, границы, идентификатор транзакции, статус и тайм-аут;
- типизированный запрос работает без процессов производителя;
- типизированная команда изменения применяет запрошенное значение;
- контрольное чтение совпадает с ожидаемым;
- исходное состояние восстанавливается, и контрольное чтение подтверждает восстановление;
- для неподдерживаемых устройств и прошивок, исключённых явным правилом допуска, не выполняется ни одной записи;
- политика конфликтов даёт предусмотренный результат: отсутствие записей или явный возврат управления;
- пройдены проверки жизненного цикла и состояний питания;
- модульные тесты используют закоммиченный набор данных.

Пока эти проверки не пройдены, оставляйте команду в виде доказательств из записи или диагностической операции только для разработчика.
